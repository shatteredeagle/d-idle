# Drag and drop onto the doll, and gear sets (TASK-380, gearsets)

User go 2026-11-12: drag gear onto the paper doll (the player's and the mercenary's), and saved named gear sets the PLAYER defines and applies. The one-week new-panel freeze was lifted for exactly this; no new panel family: both live inside the existing paper doll card of `/watch/inventory`. Tags: V verified by the offline test named, S secondary, U unverified (needs the live game). NOTHING here ran live.

## The rule that does not move
The bot never makes an equipment decision (docs/gear-policy.md, user 2026-11-10). A set is saved only when the player clicks Save and applied only when the player clicks Apply: no bot code calls `SaveSet` or `ApplySet` (V `TestGearSetsPageAndFiles` greps the bot, town, leveler and loot packages). Apply queues ordinary player commands (Equip, Take off, Take out of the stash) that run under the existing priority ladder (docs/inventory-actions.md): behind survival, at a safe moment, in the field only with nothing hostile near. The knob `resource.gearDecisions` is NOT touched: docs/gear-policy.md said the Gear Sets unlock would set it to 1, which would let the bot choose gear. The unlock opens a player feature only (correction of that section).

## Drag and drop (`web/inventory-drag.js`)
- Pointer events, not HTML5 drag and drop. A mouse starts a drag after 6 px; a finger after a 280 ms hold, so the page still scrolls (a move before the hold cancels it); during a drag the touch scroll is blocked (non-passive `touchmove`), `body[data-dragging]` is set and `inventory.js` keeps its tiles (the poll waits and paints at the end). A click right after a drop is swallowed so the menu does not open. Escape or a pointer cancel drops nothing. V: `testdata/gearsets/drag_dom.js` (node, Paladin and Sorceress views).
- Green or red comes from the SERVER's rule, the one the Equip button uses: `ItemView.canWear` (slots the request would be accepted for) plus the new `noWearSlot` (slot -> reason, every refused slot; class, level, strength, dexterity, identified, slot kind, two-hander and shield all come through `Equipper.CheckPlayerEquip`). The page decides nothing; the server checks again on the drop. Red slots show the reason on the ghost next to the pointer. V `TestViewGivesPerSlotWearReasons`.
- Drops: pack tile on a hero slot = the menu's Equip (`d2InvActions.equip`, queued, visible in the queue list, cancellable); worn item on the backpack = Take off (new `unequip` request; refused with the pack-room reason when no free spot of its size exists, `ItemView.noUnequip`); pack tile outside every card = the menu opens on its Trash CONFIRM step (a drop alone never trashes; refused items show the server's `noTrash` reason); pack tile on the stash grid and stash tile on the backpack = the stash moves (existing requests). A worn item dropped outside every card is refused with "take it off first, then trash it from the backpack" (no compound request, kept simple).
- Mercenary doll: his slots take drops and show red with `merc.actWhy` (server text): the bot has no executor for his gear yet (docs/research/merc-gear.md stage C is not built), so equip and take off for `target:"merc"` answer 409 code `merc` with that reason (V `TestMercSetsSaveAndPreviewButNoApply`, `TestGearSetRoutes`). When an executor exists and `actWhy` is empty the same drops turn green (verdict table V in `drag_dom.js`; the executor and the live behaviour are U).
- Keyboard and screen readers: the item menu already offers every action (Equip per slot, and since this card Take off on a worn item). In addition a selected backpack item (click or Enter on its tile) is worn by pressing Enter or clicking an EMPTY doll slot it fits; a refusal is read from the status line. Filled slots keep Enter = menu. Tooltips are unchanged. `focus()` always passes `preventScroll` (V by the page-rules test).
- 20 fps page: the ghost is one element moved by a transform; the target is looked up only on `pointermove` and nothing is re-laid out when the verdict does not change. U on a phone in the field (the headless pictures are V, below).

## Gear sets
### UX
Inside the doll card, under the mercenary: a name box with "Save what the hero wears" and, when a mercenary is hired, "Save what the mercenary wears"; one row per set (name, hero or mercenary, its items) with Apply..., Rename and Delete (a second click confirms). Apply... opens a PREVIEW first (V `sets_dom.js` goldens): per slot what the set names and where that item is now (`worn`, `pack`, `stash`, `elsewhere` = worn in another slot, `missing`, `blocked` with the refusal) and the steps in the order they will run; only "Apply now" queues them. The steps show in the queue card as `Set "name": Take off ...`, `Take ... out of the stash`, `Equip ... in ...`; Cancel on any queued step ends the rest of the apply, and "Cancel apply" sits on the set while steps wait. Only one apply at a time (code `queued`). Locked: the panel shows the unlock teaser instead.

### Data (state file `inventory-ui.json`, additive, versioned)
`state.sets` (a list) and `state.setsSchema` (1 once sets exist; both `omitempty`: a file from before loads as no sets, and a file without sets never writes the keys, V `TestOldStateFileHasNoSetsAndSetsRoundTrip`). A set: `{id "gs-N", name, target hero|merc, saved, slots: {slot -> SetItem}}`; `SetItem {id, code, quality, level, name, ident, where, x, y}`. At most `invdesk.maxSets` (8, 1 to 20) sets per hero, names 1 to 24 characters, unique ignoring case (V `TestSetSaveRenameDeleteAndLimits`). The state file is per hero profile, so are the sets.

### Item identity (same family as the sell marks, `docs/inventory-ui.md`, the #570 fix)
Pass one: the exact item id (exact inside one game session). Pass two (a restart renumbers every id; an identify changes the name): the same base code and the same quality or item level, preferring the item worn in that very slot, then the place and cell it was saved from, then the same name. An item is claimed once (two identical rings fill two slots). An item that was IDENTIFIED when saved must also have the same name: another item of the same base, quality and level is NOT that item and is reported missing, never substituted. One saved unidentified may have been identified since. V `TestSetApplyMissingItemIsSkippedNeverSubstituted`, `TestSetApplyItemFoundAfterRestartAndIdentify`. U live: that the name text the backend reports is stable across a restart for identified items; and two different identified items with the same name, base and quality are treated as the same item (they are the same to the player).

### Apply order (V `TestSetApplyTwoHanderAndShieldSwap`, Paladin and Sorceress)
1. Take off what must go: the item in the hand the set does not name when a two-hander and a shield would meet (the check uses the leveler's own rule through `HandsInfo`), and an item worn in another slot (a ring that moves fingers).
2. Take out of the stash what the set needs (a town errand: the bot walks home at the next safe moment; the equip steps wait behind it).
3. Equip, weapon hand first, so a two-hander to sword and shield swap frees the shield hand before the shield goes on.
The backpack must take what comes off and what comes out (simulated on the pack grid; refused with "no free spot for X: make room first" otherwise). Items missing from the pack, stash and body are skipped and counted; an item the equip rule refuses (class, level, strength) is `blocked`, skipped, with the reason. A failed step cancels the rest of its group with the reason; a fight at click time puts the step back to queued (V `TestSetApplyInAFightWaitsForTheBot`, `TestSetApplyStopsWhenAStepFailsAndCancels`, `TestSetApplyFromTheStashNeedsTheTownThenOrders`). Steps do not count against `MaxQueue` (8); an apply has its own bound of 24.
The merc: sets for him are saved and previewed the same way (his id space is separate: matched by base, quality, level and name); Apply is refused (code `merc`, the executor does not exist).

## API (`watch.inventory` schema 7, additive)
`GET /api/inventory` adds item `noWearSlot` and `noUnequip`, the `sets` block (`{schema, open, why, max, sets[]}`), `merc.actWhy`, request kind `unequip` and request fields `group`, `groupName`, `seq`. New routes, same policy gate as the other writes (origin list, token or cookie, JSON, small body, unknown fields refused): `POST /api/inventory/unequip {slot, target?}`, `/sets/save {name, target?}`, `/sets/rename {setId, name}`, `/sets/delete {setId}`, `/sets/apply {setId}`, `/sets/cancel {group}`, `GET /api/inventory/setpreview?id=`. `equip` and `unequip` accept `target: "merc"` (answered with code `merc`). All of it is in the optional `watch.InvGearDesk`; a desk without it answers code `off`, so older builds and tests are untouched. Compatibility: the schema 3 to 6 goldens are kept and compared through `strip7` (nothing renamed or removed); `testdata/sets_schema7_{Paladin,Sorceress}.json` pin the new block; old state files load. Executors: `Leveler.PlayerUnequip` (the existing `hand.Unequip` click path: click the slot, put the cursor item in a free pack cell, each step proven from memory, EnsureMainSet first, ErrBusy on a fight) and `Leveler.IsTwoHanded`. The item verbs agent's `Equipper` wrapper is untouched: unequip is a separate `Unequipper` the desk takes with `SetUnequipper`, so both executors keep working; the verbs may later add an unequip behind the same interface.
