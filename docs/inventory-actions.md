# Inventory item actions (TASK-282, itemactions; identify commands TASK-298)

Click, tap or press Enter on an item on `/watch/inventory` (backpack, stash, belt or a worn slot): a menu offers Equip, Mark for sale, Keep, Trash and (worn pinned slot) Unpin. A choice QUEUES a request; the bot performs it at the next open opportunity. A phone gets the same menu as a bottom sheet. Tags: V verified by the offline tests named, S secondary, U unverified. NOTHING here ran live.

## Request model (`internal/invdesk`)
- `Request{id, kind equip|trash, slot, target, name, state, reason, at, print}`. States: `queued` -> `doing` -> `done` | `failed` (reason); `cancelled` only from `queued`. `target` is reserved for the mercenary stage (docs/research/merc-gear.md): "" or "hero" today, the watch route answers 409 code `target` for anything else.
- The queue is persisted in `inventory-ui.json` (`queue`, `recent`), at most `MaxQueue` (8) pending, further requests refused with code `full`. A `doing` entry found at load is reported `failed` ("interrupted by a restart") and never retried: the item may have moved. V: `TestCancelBoundAndPersistence`, `TestDoingCannotBeCancelledAndRestartFailsIt`.
- Never undone: a done equip keeps its pin (no expiry), a done trash stays dropped; the bot never re-equips or picks the item up. A queued equip of an item is replaced by a trash of it; equip of a trash-queued item is refused.
- Callbacks (Snap, SellBlock, TrashBlock, Equipper, Trasher) always run with the Desk mutex released (TASK-278).

## Open opportunity (`internal/bot/playeraction.go`, U live)
`playerActionStep` runs in `runGoal` right after the points step, same predicate family: no town trip running, the hero is not walking or running (`Player.Mode` 2, 3, 6; the mode numbers are U), and either in town or in the field with `hostileNear(ClearRadius) == 0`. The click path checks again (`leveler.busy`: a live monster within 25 subtiles postpones, the request goes back to `queued`). After a postponement the step waits `playerActionGap` (10 s). The Why line shows `player_items` ("Doing what you asked on the inventory page"). V: `TestPlayerActionsRunInTownAndWaitForTheFieldFight` (fake runner).

## Equip
Slot is chosen by the page from `canWear` (one slot: plain "Equip"; two, such as both ring fingers: "Equip (left ring)" and "Equip (right ring)"). The API also takes an empty slot: the only fitting slot, else the empty one, else code `choose`. Class, level, strength, dexterity and identification checks are the existing `Leveler.CheckPlayerEquip`. Only backpack items. V: `TestAutoSlotRings` (ring fingers), `TestEquipQueuesInTheFieldAndFailureDoesNotPin`.

## Mark for sale, Keep
Unchanged (docs/inventory-ui.md); one click from the menu.

## Trash (new primitive)
- UI: the first click turns the entry into "Confirm: trash it" (plus "Keep it"); only the second click POSTs `{id, confirm:true}`; the server refuses without `confirm` (code `confirm`).
- Refused (reason shown in the menu): marked keep (`keep`, also re-checked when the request runs), worn items pinned or not (`equipped`: take it off first), stash, belt and cube items (`place`: move to the backpack), quest items, keys, tomes and the start kit (`never`, `town.NeverSellReason`). V: `TestTrashRefusals` (Paladin and Sorceress rigs).
- Click path (`leveler.PlayerTrash`): open the pack, `hand.Take` the item, `hand.DropCursor` (panels closed, left click on a free playfield cell beside the hero, up to `town.DropTries` cells), then prove from memory that the item left the pack and the cursor is empty. If no ground click worked, `DropCursor` puts it back in the pack and the request fails (`ErrNoRoomToDrop`); the item never stays on the cursor. Real input only, no memory writes. Test `TestPlayerTrash*` (Sorceress and Paladin, sim world) compiles and vets but SKIPS without game tables, so it did not run here (U).
- Ignore: a done trash records id plus fingerprint (class/quality/ilvl) and the hero position in the state file; `Desk.Ignored` feeds `loot.Looter.SetIgnore`, and the pickup skips the item without a report line. An item with the same fingerprint within 12 subtiles of the drop point also matches, because a dropped item may get a new unit id (U live). Lifetime `TrashTTL` (2 h) and at most 32 entries. V: `TestTrashRunsDropsAndIgnores`; the looter test `TestPickUpLeavesTrashedItems` skips without game tables (U).

## API (`watch.inventory` schema 3, additive)
`POST /api/inventory/trash {id, confirm}`, `POST /api/inventory/cancel {id, kind}`; both use the policy gate (origin list, token or passcode cookie, JSON, small body, unknown fields refused) like mark/equip/unpin. `GET /api/inventory` schema 3 adds item fields `noWear`, `noSell`, `noTrash` (reasons) and request fields `kind`, `target`, `print`, states `doing` and `cancelled`. Nothing removed or renamed; equip is no longer refused for "not in town" (code `town` is gone). Goldens: `internal/invdesk/testdata/view_schema3_{Paladin,Sorceress}.json` plus a test that every schema 2 key is still there and an old state file loads.

## UI (`web/inventory-actions.js`, `.css`)
Own module, listens to the `d2:inventory` event and delegates clicks, so `inventory.js` is unchanged apart from one hint text and the queue card heading. Menu is `role=menu`, entries `role=menuitem`, refused entries stay focusable with `aria-disabled` and a visible reason; arrows, Home, End, Tab cycle, Escape closes and returns focus; every `focus()` passes `preventScroll`; the popover is `position: fixed` placed by a transform, the sheet layout is a `data-mode` flag (no media query). The page's grid refreshes on its own 4 s poll; the menu and the queue card refresh at once. V: `TestItemActionsDOMGoldens` (node: 14 menu states for both classes, trash confirm, queue card, keyboard, sheet, poll stability), `TestItemActionsJSNeverScrollsOrInjects`, `go run ./tools/uilint` clean.
Extension point for drag and drop onto the doll (later pass): doll buttons already carry `data-slot` and `data-key="slot-<slot>"`; a drop handler calls `window.d2InvActions.equip(itemId, slot)`.

## Identify commands (TASK-298, API schema 5)
Identifying is a player-commanded action, not an equipment decision (docs/gear-policy.md): the bot never identifies on this path unless the player asks. Three requests, queued like the others (queued, doing, done or failed with a reason, cancel while queued, persisted, a `doing` entry found at load is reported failed):
1. **Identify** (item menu, unidentified backpack or worn items; the entry is absent on identified items and the API refuses them, code `identified`). `town.PlayerIdentify` is the chore click path (`identifyOne`: right-click the loose Scroll or the Tome of Identify, left-click the item; a worn item through its doll slot rectangle, U live). Runs in town or in the field with nothing hostile near (`town.ErrFight` postpones like the equip). Without a scroll or tome the request is refused at once and fails with `no Scroll or Tome of Identify in the backpack: use Buy identify scrolls or Identify all (Cain)`.
2. **Buy identify scrolls** (button above the queue card, with a count box; empty = fill). `POST /api/inventory/buyid {count}`. A town errand: it waits (`waits until the hero is in town` on the queue card) until the hero is in town, then `town.BuyIdentify` opens the act's scroll vendor from the act table (`Act.Shop`: Akara in Act 1, the other acts by the same table, no act number or class is named in the code), and buys by `planIDBuy`: with a tome, fill it (an explicit count is capped at its room); without one and no count, buy a Tome of Identify when the gold above the reserve covers it and fill it, else 5 loose scrolls; an explicit count without a tome buys loose scrolls. The reserve is `beltBuyReserve` (the gold reserve plus the minimal portal scroll and potion kit, the same one the belt purchase keeps) plus the repair estimate of the worn gear; every single purchase re-checks it, so nothing is ever bought below it. The result is a sentence ("bought 12 for 600 gold, short of gold for the other 8"); nothing bought because of gold fails with that reason. V: `TestPlanIDBuy`, `TestIDBuySummary`, `TestBuyScrollsErrandWaitsForTownAndReportsTheResult` (Paladin and Sorceress).
3. **Identify all (Cain)** (button, `POST /api/inventory/cain`). Locked, with the teaser `opens when Cain is rescued`, until the Search for Cain reads Done for the hero's difficulty (quest reader, memory first then the save; `Runner.QuestView`) or a Cain monster stands in the town the hero is in (`cmd/d2bot` `cainOpen`). It is a plain locked state (`d-locked` tile plus a disabled button), not a ladder row: the ladder (docs/unlock-ladder.md) prices and reveals features, and an in-game quest state needs neither. The errand (`town.CainIdentify`, in town) walks to Cain through the normal NPC open (`openNPC` over `Act.Cain`), clicks his Identify line with `PickLine` (the dialog primitive of the quest dialogs), waits until memory shows no unidentified carried or worn item and fails with a reason if some stay. No scroll is used.

### Priority and safe moment (TASK-307)
- Queue order is by priority, not by time: identify first, then equip and trash, then the town errands (`invdesk.priority`). All queued identifies run in ONE call (`Services.PlayerIdentifyBatch`: the pack is opened once, every item read, panels closed at the end). Without a scroll or tome every entry fails at once with the hint to buy scrolls.
- An identify runs at the next safe moment anywhere: `Runner.safeMoment` (no trip running, not walking, nothing hostile within the clear radius, the 10 s pause after a postponement) is the one predicate; the repair trip can call it. A fight at click time puts the batch back to queued. A queued identify that finds no safe moment within 60 s (`IdentifySafeWait`, the repair trip's `SafeWaitSecs`) fails with "no safe moment within 60 s: ask again".
- The Why line stays `player_items`, now with a `what` parameter (`identify`, `equip`, `trash`, `buyid`, `cain` or `errand`).
- The town errands (`errandTripStep`, right after the player's own actions and before the routine chores): with an errand queued and the hero in the field, the bot walks home at the next safe moment (`Town.ToTown`, as the claim trip), where the errand runs; a failed walk backs off 5 minutes. V on fakes: `TestErrandTripGoesHomeAtASafeMoment`, `TestErrandTripBacksOffAfterAFailedWalk`, `TestIdentifyPriorityAndBatch`, `TestIdentifyFightBoundAndNoTool`. The repair trip branch (agent/repairtrip) had no bot-side trip to share yet; `safeMoment` is the shared helper.

### Priority ladder (TASK playerprio; supersedes the "hero not walking" rule above)
1. SAFETY first and always: chicken, flee and the safety portal, crowd rules, a fight in progress (a hostile within the clear radius), low life, death recovery. These are the guard's existing interrupts and are checked before anything below; a safety action during a player command cancels it.
2. PLAYER COMMANDS (identify, equip, trash, buy scrolls and Cain errands, repair now): they preempt the roam, explore and travel walks. `guardOnce` (loop.go) calls `playerDue` and cancels the running action with `errPlayer`; the loop runs the command next (`playerActionStep`, `errandTripStep`, `repairTripStep`), then the walk replans or the roam resumes. The hero walking is no longer a reason to wait (`heroMoving` is gone). Interrupts are at least 3 s apart (`playerCancelGap`). Not interrupted: a town trip in progress (it finishes first, then the command runs), the farm-until-repair wait, and a safety action.
3. The bot's own chores and trips. 4. Roam, explore, farm. The guided journey (docs/campaign.md) plans inside 4: it picks the next chapter or level step and never preempts 1 to 3.
- Safe means: no town trip, the 10 s pause after a postponement is over, nothing hostile within the clear radius (`repairSafeMoment`, the repair trip's rule, shared). The log line "player action waits for a safe moment" names the rule that held it (at most every 10 s); the 60 s bound of an identify is unchanged.
- Aborting: a safety cancel or a fight cancels the context; the identify batch closes the panels on a context that survives the cancel (cursor released) and the requests go back to queued. Trash and equip clean up in their own click paths (U live).
- V on fakes (Paladin and Sorceress): `TestPlayerCommandInterruptsTheRoamWalkAndRoamResumes`, `TestSafetyInterruptsAPlayerCommandInProgress`, `TestPlayerDueNeedsAQuietFieldAndNoTrip`, `TestPlayerActionsRunInTownAndWaitForTheFieldFight`, desk ordering `TestIdentifyPriorityAndBatch`.
