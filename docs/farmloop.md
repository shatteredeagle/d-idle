> status: current (2026-11-27, farmresetretire). The loop is ALWAYS ON: the knob `bot.farmReset` was removed (flipped to default, ledger row enabled); `bot.farmResetPct` and `bot.farmResetCooldownMin` remain. ## 1. What it does

Monsters respawn only in a new game. A leveling zone that is mostly cleared pays less per minute than a fresh one, and a fresh game costs about 15 s (V, docs/levelsim.md section 2: hour 4 logs) plus the walk back. With `bot.farmReset` on, a leveling slice (`taskActs.LevelTo` -> `sweepPass`, the run kind `RunClear`; quest, boss and named runs keep roaming) that stands in a zone at `bot.farmResetPct` coverage (default 85) asks the value rule (section 2). If a reset pays, the roam ends, the hero goes to town, `startFreshGame` takes a new game (the one shared call site: the leveling slice's "everything is cleared" fresh game uses it too, and so can the Reset button of agent/botreset; that branch had no commits of its own when this was written) and the planner is sent back to the same zone (`farmReturn`: one use, same level, not over a ban, a recovery, the gear gate or a cleared area). `bot.exploredPct` is unchanged for every other zone.

## 2. The value rule (data from this run, no table constant)

`FarmResetPays(gained, fieldMin, nowRate, overheadMin)`: reset when the XP per minute of the last 3 minutes (`nowRate`) is below the average a reset yields over the cycle it would repeat, `gained / (fieldMin + overheadMin)`; `gained` and `fieldMin` are this visit's own XP and time (the first ramp-up minutes are in it), `overheadMin` is the fresh-game time (15 s until one was measured, then the last measured one) plus the walk back (the time this visit's own walk from town took, 60 s when it was not seen). I: it is the stopping rule of a renewal-reward process; it assumes the next visit repeats this one.

Guards (V: `TestFarmResetDueAndGuards`, two classes): knob on, leveling slice only, no quest, boss, named run (`D2BOT_RUN`) or gold farm order, coverage at least the knob, at least 4 minutes in the zone and 3 minutes of XP samples, cooldown `bot.farmResetCooldownMin` (5), no fresh game within 180 s of a recovery (`freshHold`) or a death, no recovery, no hostile alive, no town-portal-forbidden step, not dead, not in town; then `freshAllowed` (the no-progress bound of the fresh-game path) when the hero is home. Pause (B1) never reaches the loop (a paused bot runs no slice); the loop order and until-level orders run through the same slice, so they keep their goal. The reflex layer and equipment are untouched. Log line: `farm reset: zone <name> cov <pct> rate <x> vs fresh <y> overhead <s>`; the status sentence is the whyline `farm_reset` ("Resetting the zone: Cold Plains is 85% cleared, a fresh game refills it."); the activity header shows "(fresh game at 85%)" next to "moves on at" through `/api/hero` `explored.reset`.

Each knob row carries `value`, `default`, `min`, `max`, `unit`, `desc` and `source`: `default`, `config` (the config file's `tuning` map) or `dashboard` (an edit; kept in the tuner's `tuning.json` like every other dashboard edit, so it survives a restart). The change applies live: `bot.Tuner.Edit` replaces the shared tuning in place and the bot reads the knobs at its next zone decision (V: `TestTunerZoneClearLiveSourcePersist`; the unlocked read of a shared struct is the Tuner's documented caveat). Body: any subset of `exploredPct`, `farmReset` (bool), `farmResetPct`, `farmResetCooldownMin`, or `{"reset": true}` (all four back to their defaults, not combinable). ## 6. The sandbox thrash (2026-11-15) and its guards

Report: with `bot.farmReset` switched on in the sandbox, `Save and Exit requested (chicken / leave game)` appeared at 02:27, 02:34 and five times in 20 s at 02:42Z, no `farm reset:` line, and the minute line showed 100 percent explored in town. What the code says (V, read):
- That d2d line is written by `Proc.SaveExit` (internal/d2denv/proc.go) for EVERY `Cycler.LeaveGame`, and `NewGame` calls it: it names the chicken path only in its text. Each "Save and Exit" plus "re-entered the game" pair is one leave from any caller (`newGameRun` callers: fresh-game paths, the failsafe rung, difficulty switch, stall, drought, save point, the Reset button, chicken).
- The farm loop cannot make five leaves in 20 s: a reset needs the hero in the zone for 4 minutes with a 3 minute rate window and a 5 minute cooldown, and writes the `farm reset:` line before it acts. The missing line is consistent with the loop not being the emitter. The Reset button is a state machine that runs once per press and never starts by itself (`PlayerReset` has only the API as caller; the Needs you chip is an offer).
- Two real defects that produce exactly that burst: (1) `noTarget` (goal.go) took a fresh game without `forgetGame`; d2d has no menu poll, so the cleared set stayed, the next tick in town found nothing to do again and started another game, every few seconds (the freshGameToLevel path forgets; noTarget did not, and had no `freshAllowed` bound). (2) The nav coverage of a level survived the fresh game, and `Explored()` kept reporting the last zone's 100 percent in town, so a zone counted as explored the moment it was entered again (with `bot.exploredPct` below 100 or the loop on).
- Not provable offline which of the two the sandbox hit; the log lacked the caller. New: `newGameRun` logs `new game requested from=<file>:<line>` for every leave, so the next log names the emitter.

Guards added (V: unit tests, two classes): `farmResetDue` never acts in town, outside the visit's zone or with another area under the hero, before any pending state; a fresh game of ANY source clears the visit, the rate samples and (`Navigator.ForgetCoverage`) the roam coverage, and starts the cooldown (`bot.farmResetCooldownMin`) at that event; `Explored()` reports nothing in town; the knob flipping on starts clean; at most 3 fresh games of any source in 30 minutes, else the loop switches itself off for the session (`farm reset disabled: thrash` in the log, `Status.FarmResetOff`, an info row on Needs you); `startFreshGame` is a no-op while one is in flight and is the only fresh-game start of the farm loop, the leveling slice, noTarget and the Reset button; `noTarget` now uses it (forget, record) after `freshAllowed`. A latent deadlock found on the way (`Explored` took the runner lock inside the minute line) is fixed with an atomic. Default stays OFF until the live check passes.

## Cross-note: quest board Farm mode (slice S6)

With `quests.board` 1 the player's Farm mode (docs/questboard.md "Modes") runs the same leveling slice with the farm-gold area choice (one rung below the level's pick). It does not suppress this loop: `bot.farmReset` stays as set, because only the player's Farm gold order (`goldFarmOn`) is in the guard of `farmResetDue`. Idle mode runs no leveling slice, so no reset happens there. Not run live.
