## 1. Module layout in 1.14d and the Game.exe base

### 1.1 DLLs merged into Game.exe

- In 1.14d the former DLLs (D2Client, D2Common, D2Win, D2Gfx, D2Lang, D2Net, D2Game, D2Launch, Fog, BNClient, Storm, D2Cmp, D2Multi) are statically linked into one `Game.exe`. R (general community knowledge; consistent with the evidence below).
- Evidence in D2BS: `GetDllOffset(char* DllName, int Offset)` ignores the DLL name and does `GetModuleHandle(NULL) + Offset`. V `D2BS Offset.cpp:20-26`.
- Every pointer macro is `DLLOFFSET(a1, b1) = DLLNO_x | (b1 << 8)`, and `DefineOffsets()` rewrites each to `GetDllOffset(num)`. V `D2Ptrs.h:36-39`, `Offset.cpp:14-18, 29-35`. So **every `0x...` value in D2BS `D2Ptrs.h` for 1.14d is an RVA from the Game.exe image base**, regardless of the DLL named in the macro (D2CLIENT, D2COMMON, D2WIN, D2NET, D2LANG, STORM, BNCLIENT, D2MULTI...).
- The trailing comment `//0045ADF0-BASE` on each line is the absolute virtual address with preferred base `0x400000`. V `D2Ptrs.h:80` (`GetUnitX ... 0x5ADF0 // 0045ADF0-BASE`). S: `RVA = VA - 0x400000`. Confirmed a second time in code: `(dwTableOffset - 0x400000) + d2CommonOff` V `D2BS MPQStats.cpp:45`, and `GetDllOffset("D2Client.dll", 0x7BCBF4 - 0x400000)` V `D2BS JSUnit.cpp:454`.
- Consequence: if Game.exe loads at `0x400000` (no relocation), then `VA = RVA + 0x400000` and the D2BS number is the same as the comment address. If it loads elsewhere, you must add the actual base. Always compute `addr = base + rva`; never assume `0x400000`. R: 1.14d Game.exe has no ASLR flag, so Wine normally maps it at its preferred `0x400000`. Confirm via `/proc/pid/maps`.

### 1.2 Finding the base under Wine

Pointers are 4 bytes (32-bit process), so addresses fit in `uint32` but `/proc/<pid>/mem` is still opened by a 64-bit Go process and read with `pread(fd, buf, len, offset=uint64(addr))`.

Recipe (R unless noted):

1. Locate the process: scan `/proc/*/comm` and `/proc/*/cmdline` for `Game.exe`. Under Wine there may be several processes (wineserver, `wine-preloader`, the `Game.exe` process); pick the one whose `/proc/pid/maps` contains the 32-bit PE image. Do not use the wineserver pid.
2. Parse `/proc/<pid>/maps`. First choice: a file-backed mapping whose path ends in `Game.exe` (Wine normally maps the image from the file); the lowest address of that path's contiguous mappings is the base. R.
3. Fallback (needed whenever the image is not file-backed; the task brief says Proton/Wine D2R was observed this way, source: user brief, not verified by me): scan readable anonymous/private regions on 64 KiB-aligned addresses for `MZ` at +0, read `e_lfanew` at +0x3C, require `PE\0\0` there, then validate: `OptionalHeader.Magic == 0x10B` (PE32), `ImageBase` equals `0x400000` or the found address, `SizeOfImage` plausible. For extra confidence check `FileHeader.TimeDateStamp` (not known for 1.14d here; capture it on first run and store it as the build fingerprint). The two helper scripts already in the scratchpad (`sigscan.py`, `sigscan_mem.py`) from earlier D2R work do exactly this kind of PE-image parse and masked scan; reuse the approach. Only read them, they are not part of this project.
4. Validate by a canary: read `base+0x3A6A70` (PlayerUnit) and the first control `base+0x3D55BC` (section 2.1). In a menu the player pointer is 0 and FirstControl non-zero; in game it is the reverse. Also pin the build: hash the first 4 KiB of `.text` and refuse to run on mismatch.
5. Permissions: reading another process's memory needs ptrace access (same uid and `kernel.yama.ptrace_scope` 0, or 1 with the bot as parent/ancestor, or `CAP_SYS_PTRACE`). R. Plan for the bot to launch Wine itself (so it is the parent) or document a `setcap`/sysctl step.
6. The Wine prefix must be 32-bit-capable. A 32-bit `WINEARCH=win32` prefix is simplest; a WoW64 prefix also works. R.

### 2.4 HP, mana and stats

- D2BS calls `D2COMMON_GetUnitStat(pUnit, stat, 0)` (RVA `0x225480`, V D2Ptrs.h:306) and **shifts right by 8** for life/mana/stamina: `GetUnitStat(pUnit, 6, 0) >> 8` V `D2BS JSUnit.cpp:256-271`, `Unit.cpp:274-276`. So HP, max HP, mana, max mana, stamina are 24.8 fixed point (value/256).
- Stat ids V `D2BS Constants.h:164-222`: 0 str, 1 energy, 2 dex, 3 vit, 4 stat points, 5 skill points, 6 HP, 7 maxHP, 8 mana, 9 maxMana, 10 stamina, 11 maxStamina, 12 level, 13 exp, 14 gold, 15 stash gold, 36 damage reduction, 37 magic resist, 39 fire res, 41 lightning res, 43 cold res, 45 poison res (max variants 40/42/44/46), 67 velocity %, 80 magic find.
- External read path (no function calls): `UnitAny->pStats` (0x5C) -> `StatList` (V D2Structs.h:413-431): `+0x24 StatVec {Stat* pStats; WORD wCount; WORD wSize}`; `Stat` is 8 bytes `{WORD wSubIndex; WORD wStatIndex; DWORD dwStatValue}` (V D2Structs.h:400-411). Scan `pStats[0..wCount)` for `wStatIndex` 6/7/8/9. R: the unit's own list holds base stats; item/skill bonuses live in other lists reached via `pSetList @0x40`, `pPrev @0x34`, `pNext @0x3C` (V field offsets D2Structs.h:424-427, semantics R). `GetUnitStat` merges them. For an MVP, current HP and mana (potion thresholds) should be present in the base list; maxHP may need merging. Open question Q4.
- **CORRECTION (REPLAY canary, V on both real fixtures): in 1.14d the StatList+0x04 value is 0; the owner unit pointer is at StatList+0x44, with type at +8, unit id at +0xC and flags 0x80000000 at +0x10 (see docs/replay.md).**
- Also available: `D2CLIENT_GetUnitHPPercent(unitId)` RVA `0x79080` (V D2Ptrs.h:77); this is a function, not a variable. R: monsters on the client carry life only as a percentage (0-128) in 1.14d, so monster HP% from memory is a Q5 item.
- Status effects (frozen, etc.): `StatList->StateBits[6]` at 0x58 (V D2Structs.h:430) and function `GetUnitState` RVA `0x239DF0` (V D2Ptrs.h:307).

### 2.5 Unit hash tables: finding monsters, objects, missiles, items, tiles

- Two tables of `UnitHashTable { UnitAny* table[128]; }` (V D2Structs.h:664-666), one per unit type, 6 types each:
  - `ServerSideUnitHashTables` RVA `0x3A5E70`, `ClientSideUnitHashTables` RVA `0x3A5270` (V D2Ptrs.h:159-160).
  - S: the two bases differ by `0xC00 = 6 * 128 * 4`, i.e. exactly 6 consecutive 0x200-byte tables.
- Table `[type]` = base + `type * 0x200`; bucket = `unitId & 0x7F`; iterate `pListNext` (0xE4). V `D2BS Unit.cpp:14-37`.
- Which table: D2BS uses the **client-side** table only for type 3 (missiles); every other type (0-5) uses the **server-side** table. V `D2BS Unit.cpp:46-55`. (R: despite the name, in the 1.14d single-player/online client the "server side" table is the table of units the client knows from server updates.)
- Enumerate: for type in {1 monster, 2 object, 4 item, 5 tile} read `table[0..127]` pointers and follow `pListNext`; for missiles use the client table.
- Filtering by mode/class/name: `CheckUnit` V `D2BS Unit.cpp:238-272`. Items by location use `pItemData->ItemLocation` when "mode" >= 100 (V Unit.cpp:243-245).
- Room-local alternative: `Room1->pUnitFirst @0x74` then `pRoomNext @0xE8` (V D2Structs.h:332-348 and 662) lists units in one room; useful for "units near me" without scanning 768 buckets.
- Player's own pointer is stored separately (`PlayerUnit`, 2.1); party/roster list at RVA `0x3BB5C0` (`RosterUnit*`, V D2Ptrs.h:205; struct V D2Structs.h:216-235, 0x84 bytes, `pNext @0x80`; has `dwUnitId`, `dwClassId`, `wLevel`, `dwLevelId @0x24`, `Xpos/Ypos @0x28/0x2C`, name @0x00).

Unit modes (V `D2BS Constants.h:287-345`):
- Player: 0 death, 1 stand outside town, 2 walk outside town, 3 run, 4 being hit, 5 stand in town, 6 walk in town, 7 attack1, 8 attack2, 9 block, 10 cast, 11 throw, 12 kick, 13-16 use skill 1-4, 17 dead, 18 sequence, 19 knockback.
- Monster: 0 death, 1 stand, 2 walk, 3 hit, 4 attack1, 5 attack2, 6 block, 7 cast, 8-11 skill1-4, 12 dead, 13 knockback, 14 sequence, 15 run. "Alive and targetable" = mode not in {0, 12}. (S from the enum; the combination is my inference.)
- Object: 0 idle, 1 operating, 2 opened, 3-7 special 1-5.

### 2.6 Monster data

`MonsterData` V `D2Structs.h:548-564` (via `pMonsterData` @0x14):
- 0x16: bit flags: bit1 `fNormal`, bit2 `fChamp`, bit3 `fBoss`, bit4 `fMinion` (bit0 unknown).
- 0x1C: `anEnchants[9]` (enchant/aura list: extra strong, fast, cursed, etc. Value meanings R; table lives in the game's own enum, tabulate on a real client).
- 0x26: `wUniqueNo` (superunique id; the `hcIdx` of SuperUniques.txt, R).
- 0x2C: `wName[28]` wide name of unique/boss monsters.
- Class id (`dwTxtFileNo` of the UnitAny) indexes `monstats.txt`. Kolbot's constants for our first target: `Pindleskin = 786`, `Nihlathak = 794` V `KB modules/sdk.js:1863, 1871` (kolbot numbers follow 1.13c+/D2R-era monstats; R that they equal 1.14d numbering, high confidence since 1.14d shares 1.13 data).
- `MonsterTxt` (static data, via `D2COMMON_sgptDataTable`) is not needed for the MVP: V struct D2Structs.h:526-546.
- Immunities: not stored in `MonsterData`. They are **stats** on the monster's StatList: 37 magic, 39 fire, 41 lightning, 43 cold, 45 poison (V Constants.h:188-196), exactly how D2BS/kolbot read them (`getStat`). R: the values shown are post-difficulty resists; >= 100 means immune. Reading them needs the merged stat list (Q4). Pragmatic fallback for the MVP: hard-code immunities per monster class id from `monstats.txt` plus `anEnchants`.
- Name: `D2CLIENT_GetUnitName_I` RVA `0x64A60` (V D2Ptrs.h:247) is a register-call stub (the D2BS stub moves the arg into a register first: D2Helpers.cpp:~711-716). For an external bot, do not call it; map class id to name from your own tables.

## 3. Map and pathing data

### 3.1 Coordinate systems

- Game (world) coordinates are **subtiles** (WORD, from `Path.xPos/yPos`). A level tile = 5x5 subtiles. V evidence: `LevelMap` computes `width = level->dwSizeY*5` and `posX = level->dwPosX*5` (V `D2BS Map/Diablo_II/LevelMap.cpp:30-33`), and MAPAPI does `LevelOrigin = Level.dwPosX * 5`, `width = dwSizeX * 5` (V `MAPAPI D2Map.Core/Helpers/MapHelpers.cs:51-53`), `preset world x = room2.dwPosX*5 + preset.dwPosX` (V `MapHelpers.cs:115-117`).
- So `Level`/`Room2` positions and sizes are in **tiles** (x5 to get subtiles); `Room1`/`CollMap` positions are in **subtiles** (R/S: CollMap.dwPosGameX is subtile, V use: MAPAPI subtracts it from `LevelOrigin*...` without scaling, MapHelpers.cs:97-98).
- Pindleskin target `(10058, 13234)` in kolbot is in these subtile world coordinates (V `KB scripts/Pindleskin.js:19`).

### 3.2 Level / Room2 / Room1 / CollMap in memory

Struct offsets (V `D2BS D2Structs.h`, identical to MAPAPI's `D2Offsets.V113c` V `MAPAPI D2Map.Core/Wrapper/D2Offsets.cs:78-125`, so they hold for 1.13c and 1.14d alike):

```
Act     +0x0C dwMapSeed          +0x10 pRoom1 (first active room)  +0x14 dwAct  +0x48 pMisc (ActMisc*)
ActMisc +0x94 dwStaffTombLevel (real tomb)  +0x46C pAct  +0x47C pLevelFirst (Level*)
Level   +0x10 pRoom2First  +0x1C dwPosX +0x20 dwPosY +0x24 dwSizeX +0x28 dwSizeY
        +0x1AC pNextLevel  +0x1B4 pMisc  +0x1D0 dwLevelNo  +0x1E0 WarpX[9] +0x204 WarpY[9]
Room2   +0x08 pRoom2Near(array)  +0x24 pRoom2Next  +0x28 dwRoomFlags  +0x2C dwRoomsNear
        +0x30 pRoom1  +0x34 dwPosX +0x38 dwPosY +0x3C dwSizeX +0x40 dwSizeY
        +0x4C pRoomTiles +0x58 pLevel +0x5C pPreset
Room1   +0x00 pRoomsNear(array) +0x10 pRoom2 +0x20 Coll(CollMap*) +0x24 dwRoomsNear
        +0x4C dwXStart +0x50 dwYStart +0x54 dwXSize +0x58 dwYSize +0x74 pUnitFirst +0x7C pRoomNext

```
Reader.StaffTombLevel (internal/d2/tomb.go) uses player +0x1C pAct -> Act +0x48 pMisc -> ActMisc +0x94: S, UNVERIFIED on 1.14d (check: `act2live tombhint` vs the tomb that holds object 152).
V `D2Structs.h:209-215, 256-267 (CollMap), 269-277, 279-303, 305-330, 332-348, 350-366`.

Gotchas:
- `CollMap.pMapEnd` is documented as `+0x22` in D2BS (D2Structs.h:266) which is a typo: with 4-byte pointers it is `+0x24`. S (natural struct layout after a pointer at 0x20). MAPAPI only uses `pMapStart` and `dwSizeGame*` to bound its loop (V MapHelpers.cs:99-111), which is the safe way to read it.
- Collision cells are `WORD`, row-major, `dwSizeGameX` wide, `dwSizeGameY` tall, starting at world subtile (`dwPosGameX`, `dwPosGameY`). V read loop MapHelpers.cs:97-111.
- Static layout (Room2 list under `Level->pRoom2First`) exists once the level is initialised. `Room1` and its `Coll` exist only for rooms the client currently has "active" (near the player). To read collision for a room whose `pRoom1` is null, D2BS/MAPAPI call `D2COMMON_AddRoomData` temporarily (V `D2BS LevelMap.cpp:36-43`, `MapHelpers.cs:62-70`). **An external reader cannot call functions**; it sees collision only for rooms the client already loaded (the player's surrounding rooms, chained via `Room1.pRoomsNear`) and must cache them as they appear.
- `Act.pRoom1` (0x10) is the head of the active Room1 list; `Room1.pRoomNext` (0x7C) chains. Player's room: `player->pPath->pRoom1`.
- Level list: `player->pAct->pMisc->pLevelFirst` then `pNextLevel` (V `D2BS D2Helpers.cpp:~170-185`, `GetLevel`). `pRoom2First` is null until `D2COMMON_InitLevel`; the client already initialised the player's current and adjacent levels.

Collision flag bits (WORD) V `D2BS Map/Diablo_II/ActMap.h:45-65`, `LevelMap.h:38-57`:
`0x0001 BlockWalk`, `0x0002 BlockLineOfSight`, `0x0004 Wall`, `0x0008 BlockPlayer`, `0x0010 AlternateTile`, `0x0020 Blank`, `0x0040 Missile`, `0x0080 Player`, `0x0100 NPCLocation`, `0x0200 Item`, `0x0400 Object`, `0x0800 ClosedDoor`, `0x1000 NPCCollision`, `0x2000 FriendlyNPC`, `0x4000 Unknown`, `0x8000 DeadBody (also portal)`, `0xFFFF Avoid` (synthetic). Kolbot's names differ for some bits (e.g. `0x04 Ranged`, `0x08 PlayerToWalk`, `0x20 Casting`, V `KB modules/sdk.js:104-118`); the bit positions agree. D2BS pathing treats a cell as blocked if `(BlockWalk | BlockPlayer) & flag` V `D2BS Map/Path/AStarPath.h:46-48`. Kolbot treats `& 1` as unwalkable (V `KB core/Pather.js` via `getCollision(...) & 1`, `core/CollMap.js:233`). MAPAPI emits raw WORDs, with `-1` for unmapped cells (V MapHelpers.cs:56).

Preset units (static NPC/object/exit placement, known before the unit exists): `Room2->pPreset` list, type 1 npc, 2 object, 5 tile (V MAPAPI MapHelpers.cs:13-15, 115-141); world position as above. Level exits: preset type 5 `dwTxtFileNo` matched against `RoomTile.nNum[0]` gives the destination `Room2->pLevel->dwLevelNo` (V MapHelpers.cs:127-141). Adjacent level origins/sizes come from `Room2.pRoom2Near` (V MapHelpers.cs:73-90).

### 3.3 Reading collision from memory vs generating it with d2mapapi

| | Memory read | d2mapapi |
|---|---|---|
| Needs | only the running client | a 1.13c (or 1.09d) install's DLLs plus MPQs, run under Wine (Dockerfile in README.md:39-52) |
| Scope | only rooms currently active in the client (cannot look ahead) | the whole level, any area, from the `mapid` seed alone |
| Seed | `Act.dwMapSeed @0x0C` (V D2Structs.h:359-363) is the per-game map seed that `mapid` expects (R: d2mapapi README calls it "map id", same number) | input: `GET /maps?mapid=<seed>&area=<id>&difficulty=<n>` (V README.md:57-60) |
| Output | raw WORD cells you assemble | JSON `{levelOrigin, mapRows[][], adjacentLevels{exits}, npcs{id:[pt]}, objects{id:[pt]}, tombArea}` (V `D2Map.Core/Models/CollissionMap.cs`) |
| Risk | none to the game | works because the **1.13c DLLs** load; 1.14d has no `D2Common.dll`, so the 1.14d install cannot be pointed at it. README.md:5-6 says layouts are identical between versions for the same seed (R: 1.14d logic is the same as 1.13c, expected but untested). |

Recommendation: use memory reads for what is near you (live walls, doors, monsters, items) and d2mapapi (fed with the seed read from memory, running as a sidecar process with a separately obtained 1.13c DLL set) for whole-level planning (e.g. route to the Nihlathak's Temple entrance). For the MVP, a memory-only approach is enough because Pindleskin's area is small and the bot can path using only the active rooms plus a recorded waypoint list per area.

Open point: `MapDependsOnDifficulty = true` for 1.13c (V `D2Offsets.cs:~75`), so pass the difficulty with the seed.

### 3.4 How D2BS pathfinding consumes the map

- JS calls `getPath(area, fromX, fromY, toX, toY, reductionType, radius)`; kolbot gets back nodes and walks them with `Pather.walkTo` / teleport. V `KB core/Pather.js:504-512`, `:570`. Reduction type 0 = walk reducer, 1 = teleport reducer (V `KB core/Pather.js:504-510`). Node spacing: `walkDistance`/`teleDistance` (kolbot `Pather.walkDistance`, `teleDistance`, V `Pather.js:504-512`).
- The native side: `LevelMap` / `ActMap` builds a grid by copying every room's `CollMap` into a `width x height` matrix (V `D2BS Map/Diablo_II/LevelMap.cpp:93-120 AddCollisionMap`, `ActMap.cpp`), special-cases closed doors, objects and corpses by clearing blocking bits, then runs **A\*** (`AStarPath`) with a diagonal-shortcut heuristic (V `D2BS Map/Path/AStarPath.h:10-24` cost 10 straight, 14 diagonal) and a `PathReducer` (`WalkPathReducer`, `TeleportPathReducer`, `JSPathReducer`, `NoPathReducer`) that thins nodes to line-of-sight waypoints (V file list `Map/Path/Reduction/`). Blocked test: `(BlockWalk|BlockPlayer) & flag` V `AStarPath.h:46-48`.
- Go port plan: implement 8-way A* on `[]uint16` with the same blocked mask, then a Bresenham/LOS reducer limited to ~`walkDistance` (kolbot default R ~ 10-20 subtiles).

## 4. Input from outside

### 4.1 Coordinate transform: world to screen

D2 renders an isometric view of the subtile grid. From the engine function pair `D2COMMON_MapToAbsScreen(long*x,long*y)` RVA `0x243260` and `AbsScreenToMap` RVA `0x243510` (V D2Ptrs.h:333-334) D2BS builds:

```
WorldToScreen:  (ax, ay) = MapToAbsScreen(wx, wy);  sx = ax - GetMouseXOffset();  sy = ay - GetMouseYOffset()
ScreenToWorld:  (wx, wy) = AbsScreenToMap(sx + xoff, sy + yoff)  
```
V `D2BS D2Helpers.cpp:351-362`; the viewport offsets are variables `ViewportX` RVA `0x3A520C`, `ViewportY` RVA `0x3A5208` (V D2Ptrs.h:162-163, MouseOffsetX/Y share the same addresses D2Ptrs.h:147-149). `ClickMap` does exactly this subtraction (V `D2BS Core.cpp:140-144`).

The inner function is the standard isometric projection. **The exact formula, S derived from V code**: D2BS's own automap helper computes, with `Divisor = 1` and no offset,
`x' = ((32x - 32y) / 2 / Divisor)`, `y' = ((32x + 32y) / 4 / Divisor)` (V `D2BS D2Helpers.cpp:364-376`), i.e. `x' = 16 (x - y)`, `y' = 8 (x + y)` per subtile. R: the in-world `MapToAbsScreen` uses the same ratio:

```
absX = (wx - wy) * 16
absY = (wx + wy) * 8
screenX = absX - ViewportX
screenY = absY - ViewportY
```
Inverse: `u = (screenX + ViewportX)/16`, `v = (screenY + ViewportY)/8`; `wx = (u + v)/2`, `wy = (v - u)/2`. Treat as R until verified: place the player, read player (x,y), `ViewportX/Y`, click on a known tile, check. The player is drawn near the window centre (R: about (400,300) minus ~8 px in an 800x600 window; calibrate with the above). There are no height terms (the world is flat); only sprite pixels extend upward, so click a unit's feet (its y) not its head.

Automap mode, for a possible overlay/sanity check (V `D2Helpers.cpp:364-381`): `AutomapToScreen` uses `Offset` RVA `0x3A5198` (`POINT`) and `AutomapMode` RVA `0x311254`.

### 4.2 Window, resolution, click targets

- Resolution: variables `ScreenSizeX` RVA `0x31146C`, `ScreenSizeY` RVA `0x311470` (V D2Ptrs.h:138-139) and function `D2GFX_GetScreenSize` RVA `0xF5160` (V D2Ptrs.h:383). R: classic LoD 1.14d runs 640x480 (default) or 800x600 via the in-game/launcher setting, and under Wine windowed mode via `-w`. Read these variables at attach time and recompute the screen centre/margins; do not hard-code the resolution. Q3.
- Window handle: `D2GFX_GetHwnd` RVA `0xF59A0` (V D2Ptrs.h:382). Externally, find the X11 window by title/PID (Wine window class `D2 ...`), get its client-area origin (`xdotool getwindowgeometry` equivalent via X11/xcb), then `desktopX = clientX + sx`.
- Hit-testing UI: use `InventoryLayout`, `StashLayout`, etc. (2.7) for grid rectangles, and the constants in D2BS `Constants.h` for panel ids.

### 4.3 How to deliver input from outside (R, none of this exists in D2BS)

- D2 1.14d reads the mouse via Windows messages (R). Under Wine, the reliable external methods on Linux are: (a) X11 XTEST (`XTestFakeMotionEvent`/`XTestFakeButtonEvent`/`XTestFakeKeyEvent`) via xcb/xgb, moving the real X pointer; (b) a `uinput` virtual device (works under Wayland too, needs `/dev/uinput`); (c) `XSendEvent` to the Wine window (often ignored by Wine; avoid). Prefer (a) or (b). The window must have focus; if D2 is windowed and not focused, Wine ignores input. Q10.
- Keys: send physical key events for the hotkeys the character has set (F1-F8 for skills; number row for belt 1-4; `i` inventory, `t`/`w` etc. per default key bindings; `Esc` to close panels). Default bindings are R. A fixed, scripted profile (key bindings saved in the character, not the bot) is the sane approach; store the mapping in config.
- Timing: D2 runs 25 FPS logic (R). Use ~40 ms minimum between press and release, 50-100 ms between actions, jitter for human-ness.

```
cmd/d2bot/               main: flags, config, run

internal/map/            collision grid cache keyed by (area, room), WORD cell semantics, flags,

```

Design rules: (1) one reader goroutine produces an immutable `model.Snapshot` each 40-100 ms; goals and the dashboard only read snapshots. (2) Re-validate pointer chains every tick; discard a snapshot if a chain breaks mid-read (game loading). (3) Never write game memory; input only via the input package. (4) All RVAs live in one file with provenance comments and a `Verify()` that runs the canary checks in 7.

Milestones (each ends with something demonstrable, and each depends on the previous one):

1. **Attach and base**: find the Game.exe pid and base (section 1.2), pin build fingerprint, `Verify()` canaries. Output: "attached, base 0x..., in-menu".
2. **Read position**: `PlayerUnit` -> `pPath` -> `xPos/yPos`, area id, game-ready state machine (2.1), HP/mana (2.4, Q4 first), mode. Output: live `x,y,area,hp,mp` line at 10 Hz. Also validates the A-priori Q list items Q4/Q5 as far as possible.
3. **Read monsters**: unit hash tables (2.5), unit decode, `MonsterData`, class id, mode, position, boss/champ flags, enchants. Output: list of nearby monsters, stable ids. Add items/objects/missiles walking the same tables.
4. **Collision + transform**: read `Room1/CollMap` into the grid cache, validate against a visual/automap; implement and calibrate WorldToScreen (4.1) by clicking and reading back the target position. Output: ASCII map around the player; a click lands within 1 subtile of the request.
5. **Move**: A* + reducer, `MoveTo(x,y)` via clicks with stuck detection (position unchanged for N ticks), doors/objects. Output: walks a recorded route in town and out through a waypoint/portal.
6. **Cast**: skill hotkeys + verify via `pRightSkill`, cast at a monster with mana check, `GetSelectedUnit` hover check. Output: kills a stationary target (e.g. a Rogue Encampment dummy or a fire-resistant-safe low-level monster).
7. **Pindleskin loop**: Harrogath -> Anya red portal (object class 60 per kolbot, V `KB modules/sdk.js:1711`, `core/Pather.js:2166-2174` flow: move to Anya, talk if no portal yet, `usePortal` to area 121) -> move to `(10058, 13234)` (V `KB scripts/Pindleskin.js:19`) -> kill class 786 -> pick up drops -> go back via TP/exit -> new game. Area ids: Harrogath 109, Nihlathak's Temple 121, Halls of Pain 123 (V `KB modules/sdk.js:252, 264, 266`). Needs immunity handling for the chosen character and potion/safety logic.
8. **Goal manager + dashboard**: scheduler with priorities (safety > heal > loot > goal), retries and watchdogs, crash/timeout recovery, `internal/api` dashboard with live state, map and goal timeline.
