## 2. Conflicts and their resolution (V: cherry-pick output and the final diff)

Only ONE textual conflict: the comment above `absorb_blows` in `components/rules/combat.hpp` (cherry-pick of the damage-roll commit). The three earlier commits apply clean. The other overlaps you expected merge without a conflict, because the hunks are disjoint; each is explained here anyway.

1. **Comment above `absorb_blows` (the conflict).** 181 replaced "tools/emu/hit_absorb.py runs game.exe's own code on it" by "Its oracle (hit_absorb.py) was never committed: cited, not re-checkable" (181's new rule: a cited tool that is not in the tree is a `pr_guard` FAIL). Our commit rewrote the whole paragraph (the pool in 256ths, the absorb before the reduction, `raw`, `reduce_fine`). Resolution: our paragraph, with its last sentence taken from 181 ("Its oracle (hit_absorb.py) was never committed: cited, not re-checkable."). Semantics unchanged; code outside the comment is not involved.
2. **`monster_blow`, no textual conflict.** 181 changes the element gate from `rng(100) >= element.pct` to `(element.pct < 100 && rng(100) >= element.pct)`: an element at 100 percent no longer steps the RNG (the percent was already rolled at the swing). Our commit changes the lines above the loop only (the physical roll: `raw = low * 256 + rng((high - low) * 256)`, then `reduce_fine`, `damage = fine >> 8`, `frac = fine & 255`). The merged function keeps both: the physical roll is ONE draw as before (`rng.range(min, max)` was one draw, `rng(range * 256)` is one draw), then the elements loop with 181's gate. The draw ORDER is unchanged (physical, then the gate of each element with pct < 100, then its roll); the draw COUNT per blow is unchanged except for elements at 100 percent, where 181 removes one draw in base and head alike. The `exact` path (Corpse Explosion, Diablo's cold; ai.cpp builds its elements with pct 100) draws nothing for the physical part and, with 181, nothing for the element gate either. (V read of the merged function; V run below for the tests.)
3. **`Monster::swing_stats()` (181) against our roll.** 181 adds `swing_stats()` (copy of `stats` with the elements the swing did not roll in blanked and the rolled-in ones set to pct 100) and uses it at the swing sites (ai.cpp lines 445, 1962, 2112, 2669, 2732, `fight/pets.cpp:92`, `fight/tick.cpp:294`). Our roll reads only `a1_min/a1_max/a2_min/a2_max` of the attacker, which `swing_stats()` copies unchanged from `stats`, so it needs no change; the two `exact` sites (ai.cpp 2455 and 2493) copy `monster.stats` but overwrite the minimum, maximum and all elements, so `swing_stats()` would change nothing there either (V read). `taken.frac` and `raw` are carried by `Fight::absorb` and `settle_blow`, which 181 does not touch.
4. **`tests/test_combat.cpp`.** 181 loosens the block count `> 700` to `> 650` (the RNG stream moved by the element gate); our commit adds assertions after that line, not that one; merged without a conflict and the loosened bound stays (V: `git diff` shows `blocks > 650` in the merged file). Our new test blocks draw their own seeds, so they do not depend on the stream position.
5. **`pr_guard` finding that 181 creates for us (the reason for `-r2`).** 181's new check fails an added line that names a `tools/*.py|sh|java|cpp` file missing from the tree. Our tests cite `tools/emu/sk_mana.py` and `tools/emu/sk_tele_spot.py` (the oracles lived only in the lab): on the first on181 tree `pr_guard` reported 4 FAIL (V: Windows build worker WSL parity run, `guard.log`; the same four lines in `tests/game/test_sk_mana.cpp:9,103` and `test_tele_spot.cpp:5,52`). AGENTS.md of 181 now also says the oracle goes in the same PR; the damage roll's oracles (`tools/emu/v3_*`, `v4_*`, `mdmg2*`, `hit_absorb.py`) are not committed anywhere in the fork: the damage-roll comments were reworded to say so ("cited, not re-checkable"), which `pr_guard` accepts, but under 181's rule that claim cannot be re-checked by the maintainer.
