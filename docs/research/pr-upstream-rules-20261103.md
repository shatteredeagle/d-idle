## The rules that now apply to a code batch (V)

1. **What a batch is** (AGENTS.md section 5, "Claims may come as a batch"): "several traced claims or code changes in one pull request ... Batch from one subsystem (one research doc and the code it covers), **one claim or one code change per commit**: a code change's commit carries its test and cites its game.exe address. A row per commit in the body ... Each commit stands alone, so a reviewer can drop one and merge the rest. Keep one batch open at a time; add to it rather than opening another." `549da358` removed the old line "A code fix stays one claim per pull request": code may now be batched.
2. **Commits** (section 6): "a short subject line and at most three lines of body"; the commit is the contributor's: their name as git author, even when an agent typed it; `Reported-by:` / `Traced-by:` as last line when someone else did that part. `tools/presubmit.py` fails any co-author or AI line in a commit message (`Co-authored-by:`, `noreply@anthropic.com`, "generated with ... Claude"). Disclosure is the `Agent: <name>` line of the PR body (our commits end with `Agent: Claude Code`, which the check does not match; V, presubmit attribution ok).
3. **PR body** (`.github/pull_request_template.md`): sections What changes, Evidence from game.exe 1.14d (table Address | What it shows), **Claims (a batch only)** with the table `Commit | Claim or change | Evidence | Re-check` (one row per commit; the new first column is from `549da358`), How to re-check (paste-able commands; for an oracle the exact `tools/emu` call and inputs), Screenshots (only if visible), Checklist, then `Agent: <name>`. Fill it with `gh pr create --body-file` (the form is skipped otherwise). Leave `docs/PLAN.md` alone. `git rebase origin/main` before review and after main moves.
4. **Checks before pushing** (section 7 and `tools/presubmit.py`): `python3 tools/presubmit.py --quick` = lint, review checks, and since #180 "GCC + clang-tidy on the changed files once a build exists" (`check_gcc`: `g++ -fsyntax-only -Wshadow -Wconversion -Wno-sign-conversion -Werror` per changed TU; `check_tidy`: clang-tidy with the repo's `.clang-tidy`, failing only on lines the branch added, plus include-cleaner in changed files). It needs a `compile_commands.json` from an earlier build (`--build DIR`, default `build-presubmit`, else `build/`); without one it only warns. Full `tools/presubmit.py` (strict build, tidy, ctest) if you built. `python3 tools/pr_guard.py` (order checks on includes, Python imports, CMake lists, address tables; impossible `FUN_` addresses; binaries). `git config core.hooksPath .githooks` runs `pr_guard.py --sorted` before each push. Sorted lists: add where it sorts, not at the end. A new test is a new `test_*.cpp` with a `// test-links:` line; no file past about 1,500 lines; no one- or two-letter names.
5. **Evidence**: game.exe 1.14d is ground truth; a match needs an oracle (`tools/emu`), run by a maintainer before merging because CI has no game.exe; behaviour alone is not evidence; `FUN_` only for a function entry, `LAB_` inside a function.
6. **Review**: CodeRabbit is "an AI reviewer, not a gate"; the loop is `gh pr checks <n> --watch`, then list unresolved threads and ask the person before each reply and push. No CodeRabbit configuration in the repo and no size rule in any of the three files (V; limits in [coderabbit-limits-20261102.md](coderabbit-limits-20261102.md): file cap 100, hourly review allowance).
7. **Asking**: the agent asks before every issue, PR, comment, push or label (section 2). `security-reviewed` label needed for CI, download, network, process-launch or binary changes (our batch touches none).

## Does the bundle count as "one subsystem"? (U, our reading)

The text defines a subsystem as "one research doc and the code it covers". Our three parts sit in two docs of `docs/research/re/`: mana payment and Teleport are player skill casting (`skills.md`, code `rules/skills.hpp`, `fight/tick.cpp`, `fight/strike.cpp`, `gamedata.hpp`); the monster hit roll and absorb order are monster combat (`combat.md` / `monster-ai.md`, code `rules/combat.hpp`, `fight/states.cpp`, `ai.cpp`). Both live under `components/game/fight/` and `components/rules/`, so one batch is defensible ("the fight code"), but the doc test points to two subsystems. Mana and Teleport are the same subsystem by any reading (both: player skill use, both `Skills.txt` srvdofunc paths, the two Teleport commits share `Fight::spot`).

**Recommendation: two batches, opened one after the other** (A: mana + Teleport, 3 commits; B: monster damage roll, 1 commit). Reasons: (a) "one research doc and the code it covers"; (b) B is the part with a stated deviation (Energy Shield differs from game.exe; "never worse than base" holds with armor-first only) that a reviewer may want to drop or discuss on its own, and "a reviewer can drop one and merge the rest" is easier when the contentious part is not in the same PR; (c) "Keep one batch open at a time" means the second PR waits for the first to merge, which costs nothing here because B auto-merges on top of A (V: `git merge-tree` of the two split heads equals the bundle tree). Counter-argument for one PR: fewer round trips, size is small (17 files, +735/-62, 4 commits, far under the CodeRabbit file cap), and the rule's goal (avoid a run of PRs that conflict) is met by a single bundle; the two parts overlap in `fight.hpp` and `tick.cpp` (different hunks) so two PRs open at once would be the conflicting kind the rule wants to avoid, which is why they must be sequential. This is the user's decision.

Also note "each commit stands alone": commit 3 (nearest free spot) needs commit 2 (it edits the same `Fight::spot` Teleport branch and test), so a reviewer cannot drop 2 and keep 3; the body says so. The other pairs are independent (commit 1 touches no Teleport code; commit 4 none of the skill code).
