# Name map: our game.exe 1.14d addresses to published names (2026-11-12)

> status: research reference (card mine1). Facts only: our own `FUN_xxxxxxxx` addresses with the names other people gave the same address. Nothing is copied from those repos (no code, no tables, no text); each name is a fact with its source. The recipe at the end regenerates the full list.

Sources (all read-only, shallow clones of the default branch, deleted afterwards; licences in docs/research/awesome-diablo-mining-1-2026-11-12.md):
- **R** redivivus, https://github.com/jaenster/redivivus @ 3e2018f (2026-11-11), MIT. One `*.cpp.map` JSON per source file lists function name + address (13,513 functions). Same author and Ghidra database as libd2 (@ 00004e6), so R and libd2 count as ONE source.
- **C** recompilation specs, https://github.com/IgorKonovalov/diablo-2-recompilation @ 83c8a5b, no licence file (read only, never copy). `re/symbols.csv` has 4,603 rows; the letter in brackets is its own confidence (C confirmed, I inferred).
- **X** codex, https://github.com/Nugwa628/d2-114d-codex @ e4497e1d, MIT (decompiler output in it is not licensed by the project). Only about 1,243 of 13,085 functions are named, plus the client message table; also pairs some addresses with D2MOO names.
- **M** D2MOO, https://github.com/ThePhrozenKeep/D2MOO @ cbde180, MIT. Names are from the 1.10f code base; D2MOO has no 1.14d addresses. A name reaches our address only through X's text ("D2MOO `name`" next to a 1.14d address).

Tags. **V** = the name's meaning agrees with a finding our own docs already tag V (disassembly read, or run natively in the emulator oracle) at that address; the doc is cited. I did NOT re-run the oracle for this card: V here means "agrees with our recorded oracle result", not a new run. **S** = a published name, not checked against our evidence. **D** = sources disagree or a source looks wrong. **U** = no evidence either way. Honest limits: R is a machine reconstruction (its own README says names and types are reconstructions); 5 of its item-packet handler names are wrong (table D below), so treat any R-only name as a hint.

Coverage at origin/main f63caf9a: our docs cite 1,142 distinct `FUN_` addresses; R names 1,121 of them (the other 21 look like mid-function addresses that have no entry of their own, U), C names 957, X names 104. The V table has 33 rows; the S table below covers addresses cited 12 or more times in our docs (about 150). The other ~900 are in the regeneration recipe only.

## Regeneration recipe (no script is committed)

1. List our addresses: grep `FUN_[0-9a-f]{8}` over docs/, lower-case, unique.
2. R: walk `Source/**/*.map` of a redivivus clone; JSON fields `functions[].name`, `.address`, `.namespace`. Parse with python -I; never run anything from the clone.
3. C: `re/symbols.csv` columns address,kind,name,signature,confidence,subsystem,evidence.
4. X: `re/exports-typed/functions.tsv` (entry,name,size,callers; default names are FUN_) and `re/exports/names.tsv`.
5. Join on the 8-digit address. 1,121 of our 1,142 addresses are in R; the 21 misses are probably mid-function addresses (for example 0057c1f0, 005dabe0; U).

## Confirmations that are not names

- The address spaces are the same: R, C, X and our docs all use the 1.14d Game.exe virtual addresses (image base 0x400000), so no rebasing is needed. V: the 33 rows above.
- R's `project.json` and README say 1.14d merged the old DLLs (D2Common, D2Game, D2Client, ...) into Game.exe; that is why the module prefix in R names (D2Common::, D2Game::) tells which old DLL the function came from, a useful hint for finding the D2MOO source of a function (S, https://github.com/jaenster/redivivus/blob/3e2018f/docs/layout.md).
