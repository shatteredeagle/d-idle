## 1. GATE 2 WATCH checklist (for the coordinator, every 15 minutes)

Gate 2 = `tools/gate-run.sh 2 ...` (8 wall hours, lockstep, so about 90 virtual hours; the 2026-11-02 run gave 2811 virtual minutes in 480 wall minutes; V Gate 2 record). Virtual minute = one `minute` line. The supervisor and the soak live on the worker host; losing the coordinator session loses nothing (V gate-run.md "Resume").

### 1.1 Tick call, always (one ssh call, about 7 lines)

```
tools/gate-run.sh --status | head -12
```
Read: phase (running, fault, judging, done, failed, aborted, error), elapsed against the projected end, last poll age, `vmin`, `clvl`, kills, deaths, `restarts`, `vmin_since_kill`, `vmin_since_xp`, faults planned/done/ok (V gate-run.md "State file"). Then compute virtual speed: `vmin` delta between two ticks divided by wall minutes between them.

### 1.2 Deep call, every second tick (30 minutes), one command

Run from inside any worktree; `R` is found on the worker host, nothing is written.

```
labrun <worker-host> -- sh -c 'R=$HOME/d2d-lab/gate-run/$(cat $HOME/d2d-lab/gate-run/CURRENT); cd $R/logs; ls; tail -n 3 supervisor.log; cat fault.log 2>/dev/null; L=$(ls -t bot-*.log | head -1);
for p in "merc: " "route guard:" "kitgate-trip" "kitgate-skip" "kit: " "shop: bought" "shop: no tome" "tome not bought" "d2d portal: cancelled" "crowd-retreat" "waypoint fallback" "nav stuck" "blocked: not ready" "area skipped" "fresh game" "died" "panic"; do printf "%-28s %s\n" "$p" "$(grep -c -- "$p" bot-*.log | awk -F: "{s+=\$2} END{print s}")"; done;
grep "merc: " $L | tail -n 6 | cut -c1-220; grep "route guard:" $L | tail -n 2 | cut -c1-220; grep "\"msg\":\"minute\"" $L | tail -n 3 | cut -c1-600; tail -n 2 $R/mem.csv; df -h $HOME | tail -n 1; du -sh $R/logs | tail -n 1; uptime'
```

### 1.4 When to intervene and when to let it run

- **Let it run** (default): any single criterion that has already failed but whose evidence is still useful; a slow window under 9x that recovers; one `kitgate-skip`; one `nav stuck`. A failed gate costs the same 8 hours whether it stops at hour 2 or hour 8, but only the longer run gives the later-hour data (the clvl 15 to 16 plateau, restart acceleration, the memory curve). Stopping early saves the host, not information.
- **Stop (`tools/gate-run.sh --abort`, registry only)** when one of these holds, because the rest of the run cannot answer a new question: (1) `merc=none` at clvl 14 with `claim not seen` lines (merc fix not working; the remaining hours repeat the 2026-11-02 plateau), (2) `phase=error` / SUPERVISOR DEAD / no minute line for 10 wall minutes (nothing to watch), (3) the host is starved below 8x for 20 minutes AND the cause is another load you cannot stop (the run then measures the neighbour; abort and restart in a free window), (4) disk under 10 GB.
- **Never**: touch the slot, send input, run `pkill`, start builds on the worker host during the run, or restart d2d by hand (the supervisor owns restarts). No feature work in parallel (V gate ladder rule).
- Record each tick's one line (time, vmin, clvl, deaths, restarts, speed, signals) in the coordinator notes so the post-mortem needs no reconstruction.

### 3.2 Recommendation: Gate 3 after the A:B pilot

Order: Gate 1 (ends about 8:29 AM EST) then Gate 2 (8 h) then the A:B pilot (round 1 same evening if the result is back before 6 PM EST, round 2 next day, record by midday on day 3, V lockstep plan section 6) then Gate 3 on a clean host (the lockstep plan's decision 4 recommends the same, V). Reasons:

1. **Both need most of the host.** Gate 3 needs the host at 10x or more for 24 h; the pilot needs 3.6 cores for 2 h rounds. Together neither works.
2. **Gate 3 has the larger information value only if Gate 2 passes**, and the pilot costs 4 to 5 real hours of host. Gate 3 first would block the pilot a day; the pilot first delays Gate 3 by about 1.5 days (U).
3. **If Gate 2 fails**, Gate 3 does not start; fix cards run (offline), a rerun of Gate 1 then Gate 2 follows, and the pilot may fit in the waiting window between rungs. In that case the pilot goes between Gate 2's failure and the rerun, but not alongside the rerun (the plan's rule, V).
4. **Before Gate 3 starts**: row 11 and 1 closed (2.1), `df` and log size from Gate 2 measured, second-fault decision made, a big-run notice with the 5-minute hold sent, and a 24 h window chosen when no live agent needs the host (a weekday night is typical; the quiet-window rule for the other PC is separate).
5. The user decides the start (V gate-run.md: "The user decides when to rerun").
