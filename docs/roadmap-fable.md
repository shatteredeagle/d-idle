## Standard enable rule (user decision 2026-11-26)

Flip, watch 2 h, auto-revert: a dark feature is switched on the sandboxes as soon as its scenario, drill or replay passes; the invariant monitor watches for a 2 h window (user decision 2026-11-27: no 24 h waits); a HARD invariant breach (a death, a stall, a potion not drunk, a refusal-as-failure storm) reverts the knob automatically; otherwise it stays on and the ledger row closes. No criterion needs more than the 2 h window of live observation; longer evidence comes from scenarios and replays. The owner of every flip is the coordinator, due next session. The tool is card `autorevert1`; until it exists the coordinator reverts by hand when the monitor reports a hard breach.

## Operating rule

Before the coordinator approves a new patch card (a `bug` or `bot-fix` card for the bot), the coordinator names its cause class (A to K of review 2026-11-25 section 2.2: A two deciders undo each other, B refusal counted as failure, C supply and economy, D navigation geometry, E stale state after portal, death or new game, F a fact the backend lacks, G threshold moved by one incident, H per-quest special case, I class-specific combat, J tests and flakes, K not visible) and checks that class against this tracker and `data/darklaunch.json`. If a row covers the class (see the "kills" column of section "Cause class to row" below), the fix card is attached to that row (its id goes into the row's card cell and the card says so in its description) and the question asked is "does the row's flip remove this cause?", not "what number do we move?". A fix card that repeats a class whose row is `built-dark` needs the coordinator to state why the row has not been flipped, or it waits. A fix card may not add a knob without removing one or the owner's word (P10). Class D (navigation geometry) is the only class this rule does not redirect: it is the game's own complexity and keeps being fixed case by case with a fixture each time (review 7.4).

## How to keep this file true

- On each merge that touches a row's card: update STATE, evidence (commit or doc) and next action in the same PR as the coordinator's merge bookkeeping, not in the feature PR (the feature agent does not own this file).
- A row moves to `trial` when the knob is set on a sandbox; to `enabled` only when the default changes and the ledger row says `default-on`.
- A row with `built-dark` past its `review_by` appears in `report.py` as due; the decision is enable, extend (with a changed why) or retire.
- Drift check (a WARNING, never a failure): `python3 -I tools/roadmap/check.py` reads the `card` and `STATE` cells of every table here against `backlog/tasks/` and the merge subjects on `origin/main`. It warns when a row says `not started` while one of its cards is Done or merged (S1), when a row says `not started` or `in flight` while every card it names is Done with every box ticked (S2), and when a card cell names no known card (S3). Run it before and after editing this page and at each coordinator merge tick; a warning is answered in the same edit by moving the STATE or by naming the open card that holds the rest (or, when the rest has no card in this repo, `(open: why)` in the card cell). `--rows` prints what it found per row and the tally of states, so no count is typed here.
- The check cannot see a card merged under another branch name (`dlvwave3` carried five dlv cards, `townrest` two town cards, `pgcards2` the nightly and earned cards) while its card is not Done, nor a row whose evidence text went stale. So: name every card of a row in its card cell, and when a branch carries several cards, write each card id in the merge subject.
- A cell cites a knob by name in `docs/knobs.md`, never by line number.
